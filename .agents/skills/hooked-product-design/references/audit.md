# Audit an existing product

This workflow operationalizes the whole Hook Model. Read the phase reference only when deeper diagnosis is needed.

## Establish scope and inspect the real experience

Identify the requested surface, audience, useful outcome, natural cadence, and available evidence. Inspect existing product documentation, screens, copy, states, flows, and analytics if available. Respect application ownership. A request to audit does not itself authorize rewriting the entire product.

Reconstruct first use, ordinary return, a successful result, interrupted/error recovery, and lapse/restart as relevant to scope. Distinguish observed experience, code-supported behavior, user reports, and assumptions. Do not rate an unseen screen as if inspected.

## Map one loop at a time

For each meaningful recurring behavior record:

| Need and context               | Cue                       | Smallest action      | Actual reward                       | Investment                         | Next value/cue                  |
| ------------------------------ | ------------------------- | -------------------- | ----------------------------------- | ---------------------------------- | ------------------------------- |
| User wants to improve a tactic | Contextual practice entry | Attempt one exercise | Understand the tactic from feedback | Save progress or choose next level | Resume an appropriate challenge |

This is an illustrative learning-product loop, not a claim about current Quitapon features. Multiple modes may have separate loops; do not combine incompatible user purposes into one fictional journey.

## Locate the failing transition

| Observed pattern                      | Candidate bottleneck                       | Next evidence/change                     |
| ------------------------------------- | ------------------------------------------ | ---------------------------------------- |
| Relevant need but no useful starts    | Access or cue                              | Check timing and entry point             |
| Many starts, few meaningful actions   | Ability or unclear benefit                 | Observe decisions, reduce friction       |
| Many actions, low satisfaction        | Reward quality or mismatch                 | Compare expectation with actual outcome  |
| Good first result, weak return        | Cadence, continuity, or next-value failure | Examine next need and invested value     |
| Frequent visits, little useful result | Proxy/incentive loop                       | Measure benefit separately from activity |
| Drop-off after a missed day           | Pressure or restart burden                 | Preserve work and offer a small return   |
| Return only after many alerts         | Prompt dependence or weak intrinsic value  | Test fewer cues and improve usefulness   |

These are hypotheses, not proof. Poor audience fit, reliability, accessibility, connectivity, and unavailable content can produce similar patterns.

## Product actions

| ID    | Audit action                                      | Reviewable artifact                   |
| ----- | ------------------------------------------------- | ------------------------------------- |
| AU-01 | Define one useful behavior and cadence            | Behavior statement with evidence      |
| AU-02 | Capture actual loop and gaps                      | Short map linked to screens/events    |
| AU-03 | Count waits, decisions, input, and recovery       | Before/after journey                  |
| AU-04 | Compare promise to realized benefit               | Reward mismatch finding               |
| AU-05 | Inspect saved value and next-session use          | Continuity/persistence finding        |
| AU-06 | Review each relevant message and refusal state    | Copy changes plus trigger logic       |
| AU-07 | Compare habitual, new, and lapsed paths           | Candidate habit path and alternatives |
| AU-08 | Rank narrow changes by useful impact and evidence | Prioritized backlog                   |
| AU-09 | Define validation and removal criteria            | Focused experiment/acceptance plan    |

## Prioritize without false precision

Use high/medium/low judgments for expected user benefit, confidence, affected users, effort, and downside. Note the evidence behind the ranking. Scores are optional planning aids, not measurements of psychological effectiveness.

Prefer fixing absent/broken value and clear usability obstacles; then improve reward recognition, continuity, and relevant return. Use discovery when the need is unproven, a prototype when usability is uncertain, and a cohort experiment when behavior effects are uncertain. Avoid building the entire catalog.

## Turn findings into changes

For each selected item state: observed issue; user/context; phase; supported mechanism; exact change; sample proposed copy where needed; persistence/permission implications; primary outcome; guardrail; and smallest validation step. If code changes are requested, name the owning files and honor the app's design and verification requirements.

Make a focused audit short. For comprehensive audits, cover all four phases, habit suitability, autonomy, measurement, edge states, and alternative explanations. Distinguish urgent blockers from worthwhile experiments and longer-term opportunities.

## Close the requested scope

Deliver the concrete audit, redesign, text, or implementation requested. State what was observed, what was inferred, and what remains unmeasured. Do not imply that a compelling recommendation is already a validated improvement. Use [deliverables](deliverables.md) only if a reusable output shape would help.
