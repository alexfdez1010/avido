# Reviewable product deliverables

These output shapes are practical extensions. Choose only the shape needed for the request, adapt its length, and avoid dumping all templates into a response.

## Quick improvement or focused copy edit

Lead with the concrete proposed change or final copy. Explain the current friction, supported mechanism, and one useful verification. Include functional dependencies when text promises behavior. Do not expand a button edit into a comprehensive retention program.

## Comprehensive audit

Include:

1. Scope, observed sources, audience, beneficial behavior, cadence, and uncertainty.
2. Actual loop map with weak/missing transitions and alternative explanations.
3. Prioritized findings, each with evidence, precise change, copy where appropriate, and validation.
4. Habit suitability, reward relevance, investment/continuity, and autonomy conclusions.
5. The smallest appropriate next action and what would establish benefit.

Suggested findings table:

| Priority | Surface and observed issue                | Evidence/confidence | Hook mechanism | Concrete change                      | Proposed copy        | Outcome/guardrail                   |
| -------- | ----------------------------------------- | ------------------- | -------------- | ------------------------------------ | -------------------- | ----------------------------------- |
| High     | Starting task requires unfamiliar choices | Observed; medium    | Action/ability | Recommend a reversible starting task | Start a guided round | Useful completion / mistaken starts |

Distinguish observed defects from hypotheses and optional opportunities. Avoid aggregate numerical scores that suggest an unvalidated psychological measurement.


Use a diagram only when it helps explain the flow. A new product may have a hypothesized loop; label it accordingly.

## Copy specification

```text
Surface, placement, locale, and user state:
Existing wording or problem:
User need and expected next action:
Recommended title/body/helper text:
Primary and secondary labels:
Dynamic fields and missing-data fallback:
Action destination and actual effect:
Permission, privacy, persistence, or preference requirements:
Loading / success / error / empty / interrupted states relevant here:
Reason for wording and required flow changes:
Validation: comprehension / useful completion / guardrail:
```

For messages add eligibility, timing, cadence cap, expiry, quiet periods, suppression, and preference route. For several strings, use a compact table keyed to placements/states, not a pile of unassigned slogans.

## Experiment card

```text
Question and evidence:
Hypothesis: change → mechanism → useful behavior:
Audience and eligibility:
Comparator and assignment unit:
Single material intervention:
Primary metric, denominator, window, and cohort maturity:
Guardrails and segments to inspect:
Instrumentation and known limitations:
Duration/sample rationale from actual inputs:
Decision-worthy effect and uncertainty:
Stopping / rollback conditions:
Decision: continue / revise / remove / gather evidence:
```

Do not invent numbers or claim a randomized result from observational cohorts. Drafting a card is distinct from running it in production.

## Prioritized implementation backlog

Each item should contain a concrete user problem, target surface, evidence, minimal change, owning app/module, copy/state requirements, acceptance condition, and validation. Include dependencies only when real.

Example acceptance condition: **After an interruption, the user can resume the last persisted useful step, see its actual saved state, and recover if restoration fails.** This is more reviewable than increase retention.

Do not add a platform migration, analytics system, messaging channel, or gamification layer unless necessary and requested. In Quitapon, keep implementation in the owning app and apply its UI contracts and required checks.

## Workshop output

Record selected need, cadence, loop, candidate changes, evidence gaps, and chosen next test. Retain rejected options only when their reason prevents confusion. Convert ideas into a small ranked set rather than treating every brainstorm as committed work.

## Completion and evidence report

State what was delivered, what checks or observation were actually run, and what remains unmeasured. A validated skill structure does not validate a product hypothesis. A successful task test does not prove long-term habit formation.

Keep final communication in the user's language and requested depth. Store supporting detail in appropriate project artifacts only when requested or required by repository conventions.
