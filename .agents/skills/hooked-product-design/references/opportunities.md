# Find useful habit-forming opportunities

Book basis: chapter 8. Evaluation cards and action IDs are practical extensions.

## Start with existing needs and workarounds

Observe your own routine as one evidence source, then test against real intended users. Look for frequently repeated work, improvised notes, manual coordination, repeated context entry, and the point where a person wishes a task were easier. A workaround demonstrates a candidate need, not a market by itself.

The Buffer example in the book illustrates an existing sharing behavior with burdensome scheduling. The lesson is to remove unnecessary steps from a desired routine, not to build another social scheduler by default.

## Four lenses

| Lens                | Investigate                                              | Opportunity signal                         | Disconfirming evidence                                          |
| ------------------- | -------------------------------------------------------- | ------------------------------------------ | --------------------------------------------------------------- |
| Personal need       | Where does your own routine repeatedly fail?             | Direct knowledge of a useful workaround    | Other intended users do not share it                            |
| Nascent behavior    | What do early adopters repeatedly do that looks unusual? | Small group solves a broad underlying need | Demand depends entirely on novelty or subsidy                   |
| Enabling technology | What infrastructure/platform removes a prior constraint? | A useful action becomes feasible/easier    | New cost, privacy burden, or unreliability cancels the benefit  |
| Interface change    | What interaction reduces decisions or effort?            | Existing need becomes usable in context    | Interface novelty adds learning cost without useful improvement |

The book's infrastructure → enabling technology/platform → application sequence explains opportunity timing. It does not require adopting the newest platform. Verify current technical capabilities from official sources before implementation.

## Opportunity card

Capture target user, recurring need, existing routine, present constraint, enabling change, smallest action, actual benefit, meaningful stored value, cadence, current alternatives, assumptions, possible downside, and cheapest disconfirmation.

Prefer a narrow feature improving the current product when the user's task is product improvement. Do not turn opportunity discovery into a request to replace the company, replatform, or build a speculative ecosystem.

## Illustrative opportunities for a learning game

- An interrupted practice round could resume with its last useful context, if actual persistence supports it.
- A learner unsure where to start could receive one appropriate suggested exercise, with another option visible.
- Saved explanations could become a review collection rather than disposable end-screen text.
- A player wanting social feedback could deliberately share a position with a chosen audience.
- Someone returning after a gap could start with a refresher rather than a backlog or guilt message.

These are hypotheses for investigation, not assertions about Quitapon's present capabilities or a backlog to implement automatically. Use the owning app's product documentation before proposing code changes.
